?
Rate Limiter Manager Decision
Sequential check through all 4 rate limiting tiers - if ANY tier rejects, request is blocked
Sequential Checks Fail-Fast Logic Fail-Open on Errors
⬇️
4-Tier Rate Limiting Sequence
Tier 1: Request Rate Limiter
Check if user has exceeded requests per second/minute limit
Check: Token Bucket Algorithm
Storage: Redis Lua Script
Reject: HTTP 429
Tier 2: Concurrent Requests
Check if user has too many active requests
Check: Active Connection Count
Storage: Redis Sets
Reject: HTTP 429
Tier 3: Fleet Usage
Check if system capacity is reserved for critical requests
Check: Critical vs Non-Critical Ratio
Storage: Redis Counters
Reject: HTTP 503
Tier 4: Worker Utilization
Check if server workers are overloaded
Check: Worker Capacity & Queue Depth
Storage: In-Memory Metrics
Reject: HTTP 503
⬇️
3
Rate Limit Decision
Based on the checks above, the request is either allowed to proceed or rejected with appropriate status code
Decision Response Headers Added Metrics Recorded
❌ REJECTED
Request blocked by rate limiter
• Return HTTP 429/503
• Add rate limit headers
• Log rejection reason
• Update metrics
✅ ALLOWED
Request passes all checks
• Proceed to application
• Track concurrent request
• Update counters
• Record metrics
⬇️
4
Application Processing (If Allowed)
Request proceeds to business logic, database operations, and response generation
Business Logic Database Query External APIs Response Generation
⬇️
5
Request Cleanup
Remove request from concurrent tracking, update metrics, and send response to client
// Cleanup concurrent request tracking go manager.ConcurrentLimiter.ReleaseRequest( context.Background(), req.UserID, req.Endpoint, req.RequestID, )
Key Implementation Details
Fail-Open Architecture:
If Redis is down or any limiter fails, requests are allowed through to maintain API availability
Atomic Operations:
Redis Lua scripts ensure atomic token bucket operations and prevent race conditions
Performance Target:
Entire rate limiting check completes in <5ms with 10,000+ requests/second throughput
Priority Classification:
Critical → POST → GET → Test Mode (higher priority gets better treatment)
